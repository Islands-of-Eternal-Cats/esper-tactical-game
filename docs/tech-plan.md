# Техплан среза «Ржавый»

NINE LIVES CORP · инженерный документ. Дизайн среза — в отдельном плане прототипа

## Область

Здесь только то, как это устроено и в каком порядке пишется. Что именно делает Ржавый, почему клик — это намерение и какие числа у куч — в плане прототипа; сюда это не дублируется.

## Стек

| Слой | Чем | Почему |
| --- | --- | --- |
| Ядро | TypeScript, фиксированный шаг, Web Worker | воспроизводимость важнее всего остального |
| Сцена | Three.js, WebGL2 | библиотека рендера, не движок: не претендует на цикл и состояние |
| Интерфейс | голый DOM в срезе, Svelte когда появятся списки | до первого меняющегося списка фреймворк не нужен |
| Сборка | Vite | воркеры и wasm из коробки, tree\-shaking для Three.js |
| Ассеты | Blender → glTF | плоская заливка, без текстур |

WebGL2, а не WebGPU: охват шире, а плоской заливке WebGPU ничего не даёт.

## Структура проекта

```
src/
  shared/
    protocol.ts      Command, Snapshot — единственный общий словарь
  core/              симуляция; не знает про DOM, three и svelte
    sim.ts           состояние и тик
    grid.ts          клетки, соседство, A*
    jobs.ts          очередь задач и резервирование
    rng.ts           свой ГПСЧ с явным сидом
  worker/
    sim.worker.ts    цикл, приём команд, отправка снапшотов
  render/            three.js; читает снапшот, ничего не меняет
    scene.ts  camera.ts  kit.ts  cats.ts
  ui/                DOM; читает троттленный снапшот
  main.ts
```

**Запрещённые зависимости.** `core` не импортирует ничего, кроме `shared`. `render` и `ui` не импортируют друг друга. Никто не импортирует `core` напрямую из главного потока — только через воркер.

Это стоит закрепить правилом линтера сразу: нарушение появляется тихо и всплывает через полгода как рассинхрон.

## Контракт сообщений

Единственное, что пересекает границу. Всё остальное — внутренние детали своей стороны.

```ts
// главный поток → воркер
type Command =
  | { t: 'setSpeed';  speed: 0 | 1 | 2 | 3 }
  | { t: 'setZone';   cell: Cell; radius: number }
  | { t: 'clearZone' }
  | { t: 'reset';     seed: number }

// воркер → главный поток
interface Snapshot {
  tick:   number
  cats:   CatView[]
  piles:  PileView[]
  zone:   { cell: Cell; radius: number } | null
  totals: { remaining: number; collected: number }
}

interface CatView {
  id:       string
  cell:     Cell          // текущая клетка
  next:     Cell | null   // следующая; рендер интерполирует между ними
  progress: number        // 0..1, приводится к float только здесь
  facing:   Dir
  action:   'idle' | 'walk' | 'work' | 'haul' | 'dump'
  lookAt:   Cell | null   // цель внимания — для поворота головы
  status:   string        // «доканчивает кучу», «пылесос полон»
  load:     number
  capacity: number
}
```

Три поля несут больше, чем кажется. `cell` \+ `next` \+ `progress` — это весь договор о том, как дискретная симуляция становится плавной картинкой. `action` — единственный источник выбора анимации; ввод игрока на него не влияет напрямую. `lookAt` даёт поворот головы, то есть видимое внимание.

## Цикл симуляции

```ts
const TICK_MS = 50            // 20 тиков в секунду
const MAX_STEPS = 8           // защита от догоняния после сворачивания вкладки

let acc = 0, last = performance.now()

function frame() {
  const now = performance.now()
  acc += (now - last) * speed // speed: 0 = пауза
  last = now

  let steps = 0
  while (acc >= TICK_MS && steps < MAX_STEPS) {
    core.tick()               // без аргументов: шаг всегда TICK_MS
    acc -= TICK_MS
    steps++
  }
  if (steps > 0) post(core.snapshot())
}
```

Ключевое — **`tick()` не принимает время**. Ускорение ×3 означает втрое больше тиков, а не втрое больший шаг. Именно поэтому результат на всех скоростях одинаковый; если хоть где\-то в логику попадёт дельта, это свойство исчезнет.

`MAX_STEPS` спасает от спирали смерти: вкладка была свёрнута минуту, аккумулятор набрал минуту, без ограничителя воркер уйдёт в неё догонять и повесит вкладку.

## Детерминизм

Правила для всего, что лежит в `core`\:

- Собственный ГПСЧ (xorshift или PCG) с явным сидом. Сид хранится в состоянии и попадает в сохранение.
- Ни `Math.random`, ни `Date.now`, ни `performance.now` внутри `core`.
- Порядок обхода детерминированный: массивы с явной сортировкой по `id`. Не полагаться на порядок вставки в `Map`/`Set`.
- Накопление состояния — в фиксированной точке (целые в тысячных долях), не в плавающей.
- Позиции — целые координаты клеток. Float появляется только на границе, в `progress` для рендера.

**Как проверяется.** Прогон N тиков от одного сида на скорости 1 и на скорости 3, сравнение хеша состояния. Это автотест, а не ручная проверка, и он пишется на M0 — раньше, чем появится сцена.

## Рендер

- Ортографическая камера, зафиксированный изометрический угол, без вращения. Зум 0,7–1,4 под размер экрана, панорама.
- `InstancedMesh` для всей повторяющейся геометрии кита. Решается на M1, задним числом переделывать больно.
- Теней нет; при плоской заливке форма читается затенением по нормали. Постобработки нет.
- `devicePixelRatio` ограничен 1,5–2.
- Обработка `webglcontextlost` / `webglcontextrestored` — мобильные браузеры убивают контекст при сворачивании.
- Ввод через Pointer Events. Ни одной критичной подсказки только по наведению.
- Микшер анимаций получает **реальное время кадра, умноженное на множитель скорости**. Никогда — дельту из аккумулятора симуляции.
- Позиция кота на экране: линейная интерполяция `cell → next` по `progress`. Сетку игрок не видит.

## Интерфейс

Снапшот раздваивается: рендер читает сырой каждый кадр, интерфейс получает троттленную копию на 10–15 Гц. Больше человек всё равно не воспринимает, а перерисовка дерева компонентов на частоте кадров — просто сожжённый бюджет.

Состояния игры в слое отображения нет. Снапшот кладётся в `$state.raw`\: отслеживается подмена ссылки, а не каждое поле каждой кучи. Объекты Three.js в реактивность не попадают никогда.

В срезе интерфейс — строка состояния, счётчик, пауза, две кнопки скорости. Это полсотни строк голого DOM. Svelte появляется, когда появится первый **меняющийся список**\: панель докладов или ростер. Строка состояния списком не считается.

## Ассеты

### Правило разделения: скиннинг против сокета

Два способа собрать персонажа из частей, и стоят они принципиально по\-разному.

**Скиннингованная часть** — голова, корпус, одежда как отдельные меши на общем скелете. Требует одинакового скелета, совпадающей bind\-позы, покраски весов и совпадения вершин на стыке.

**Пропс на сокете** — вещь, прикреплённая к кости. Риггинга не требует **вообще**\: ни весов, ни стыков.

Правило: в сокеты уходит всё, что туда влезает. На дистанции камеры разницы не видно, а стоимость отличается на порядок.

### Разбиение кота

| Часть | Как | Сколько |
| --- | --- | --- |
| Голова | скиннинг | уникальна на кота: 1 в срезе, \~12 за кампанию |
| Корпус | скиннинг | 1–2 общих архетипа, базовая одежда встроена |
| Снаряжение | сокет | несколько на всю игру, комбинируется свободно |
| Предмет в лапе | сокет | по одному на тип работы |
| Акцентный цвет | параметр материала | новой геометрии ноль |

Идентичность несёт голова — порода, уши, морда. Тела под спецовками почти одинаковы, поэтому уникальным делается только то, что различает котов.

Массивность выражать одеждой, а не телом: каждый новый архетип корпуса умножает всю скиннингованную одежду, и это самая недооценённая статья расходов в модульных персонажах.

### Откуда берутся модели

1. **Шаги 1–5 — ассетов нет вообще.** Пол, стены, кучи и кот — примитивы, созданные прямо в коде Three.js. Blender не открывается. Проверка ядра не должна ждать художника.
2. **Кит окружения** — около двадцати мешей: полы (3), стены (4), перекрытие, трубы и вертикали (4), пропсы (9). Моделятся руками. Генерацией **не** делаются: смоделировать ящик быстрее, чем починить сгенерированный и перестроить ему топологию.
3. **Кот** — низкополигональная модель по сгенерированному концепту. Моделить руками: чистая топология важнее скорости, потому что к ней потом крепится скелет. Image\-to\-3D (Tripo, Meshy) оправдан только на сложных «геройских» пропсах, где чистка быстрее моделинга.
4. **Риг** — автоматический. Работает, потому что коты антропоморфные, то есть biped: Tripo, Meshy, AccuRig или Mixamo. Известная мина: у Meshy плывут веса таза, из\-за чего ноги скользят при ретаргете — проверять на ходьбе сразу, до того как вокруг модели построено полгода работы.
5. **Анимации локомоции** — готовые из Mixamo, ретаргет. Скелет один на всех котов, поэтому клипы переиспользуются целиком.
6. **Рабочий цикл строится от предмета.** Анимируется путь пылесоса, лапы подтягиваются к точкам хвата через IK, всё запекается в ключи в Blender. Отдельный захват или генерация «работы» не нужны. Запасной путь при росте числа движений — видео\-мокап с телефона плюс чистка.
7. **Хвост и уши** — своя цепочка костей: пружина в Blender или синус с отставанием в коде. В humanoid\-ригах их нет, Mixamo не даст ничего.
8. **Портреты** — генерация нейросетью, уже готовы. 512 px WebP, \~14 КБ штука.

Граница генерации: концепты, портреты, промо — да. Геометрия кита и котов — нет.

### Бюджеты и настройки экспорта

|  |  |
| --- | --- |
| Модуль кита | 50–300 треугольников |
| Кот целиком | 600–1200 треугольников |
| Пропс на сокете | до 200 треугольников |
| Текстуры | нет ни одной; только плоские материалы |
| Экспорт | glTF/GLB, \+Y вверх, модификаторы применены, скиннинг включён, сжатие Draco или meshopt |

### Файлы

- `character-kit.glb` — скелет, все головы, корпуса, снаряжение одной иерархией. Лишнее гасится видимостью на рантайме.
- `animations.glb` — клипы, общие на всех котов.
- `env-kit.glb` — модули окружения.

Отдельные файлы на каждую часть с последующей сшивкой **не делаем**\: расходящиеся bind\-позы — самый неприятный класс ошибок здесь. При наших размерах (голова \~20 КБ) грузить всё одним файлом дешевле, чем ловить эти ошибки.

Имена мешей — часть контракта, по ним код гасит видимость: `head_rusty`, `body_stocky`, `gear_vacuum`, `held_vacuum`. Сокеты адресуются именами костей.

### Дисциплина авторинга

Один эталонный `.blend` с базой и скелетом. **Все** новые части создаются копией из него — не с нуля, не импортом со стороны.

Одна съехавшая bind\-поза ломает всех котов сразу, и обнаруживается это обычно после того, как сделано двенадцать голов. Это не техническая проблема, а процедурная, и лечится только правилом.

## Сборка и раздача

- Воркер подключается как `new Worker(new URL('./sim.worker.ts', import.meta.url), { type: 'module' })` — Vite соберёт его сам.
- Между воркером и главным потоком — обычный `postMessage` со структурным клонированием. `SharedArrayBuffer` не берём: он требует заголовков COOP/COEP и сужает варианты хостинга.
- Звук грузится лениво и в бюджет начальной загрузки не входит.

### Бюджет загрузки

| Статья | По сети |
| --- | --- |
| Three.js, tree\-shaken | 100–150 КБ |
| Ядро и интерфейс | 50–100 КБ |
| Кит окружения | 50–80 КБ |
| Меши котов | \~120 КБ |
| Скелет и анимации | 50–150 КБ |
| Портреты | \~14 КБ штука |

Итого **0,5–0,8 МБ** на всю игру; срез заметно меньше. Причина одна: текстур нет, а именно они раздувают веб\-сборки.

Порог проверяется автоматически при сборке, иначе он уползает незаметно. Для сравнения: у порталов начальная загрузка ограничена 8 МБ (Poki) и 20 МБ для мобильной главной (CrazyGames) — то есть запас примерно десятикратный.

Отдельная статья, о которой легко забыть, — **звук**\: пара минут музыки и эмбиента весит больше всей остальной игры.

## Порядок реализации

| Шаг | Что | Готово, когда |
| --- | --- | --- |
| 1 | `shared/protocol.ts`, `core/rng.ts`, `core/grid.ts` | A\* находит путь в тестах |
| 2 | `core/sim.ts`, `core/jobs.ts` с резервированием | кот убирает двор, лог в консоль |
| 3 | Воркер, цикл, команды, снапшоты | тест детерминизма зелёный на ×1 и ×3 |
| 4 | `render/` на примитивах, камера, интерполяция | двор виден, кот едет плавно |
| 5 | Клик → `setZone`, строка состояния | вмешательство работает и объясняется |
| 6 | `character-kit.glb`, анимации, look\-at | кот вместо капсулы |
| 7 | `env-kit.glb`, палитра, лампы, инстансинг | выглядит как игра |

Шаги 1–3 отвечают на технический вопрос, шаги 4–5 — на дизайнерский. Шаги 6–7 делают ответ честным: на капсулах характер не оценивается.

## Автоматические проверки

- **Детерминизм** — одинаковый сид на разных скоростях даёт одинаковый хеш состояния.
- **Сохранение** — загрузка не позволяет перебросить зафиксированный исход: сид и состояние ГПСЧ восстанавливаются вместе с состоянием.
- **Бюджет сборки** — размер начальной загрузки не превышает порог.
- **Границы модулей** — правило линтера на запрещённые импорты.
